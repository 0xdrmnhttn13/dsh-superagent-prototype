# Superagent Investigator

A standalone, local engineering investigation agent. The Superagent domain Engine owns persistent Triggers, Threads, Policy, Mandates, Tickets, Assignments and reports in SQLite; [Pi Coding Agent](https://pi.dev/) supplies model reasoning. No DeepSeek Harness server, profile, executable, or Cordis plugin is required.

> Research prototype, not an OS sandbox. Submit synthetic or approved data only. A configured Pi model receives investigation text and any evidence the investigator reads.

## Requirements

Node.js 22.19+ or 24+, pnpm 11.7+, a supported Pi model with existing authentication (for example `pi` → `/login` → `/model`). The service uses Pi's installed `~/.pi/agent/auth.json` and model catalog. No additional paid provider or DeepSeek key is needed.

```sh
pnpm install --frozen-lockfile
pnpm check
pnpm link --global                       # optional: installs `sa`; alternatively use `node scripts/sa.mjs`
sa start --state-dir "$HOME/.superagent"
sa status --state-dir "$HOME/.superagent"
printf '2026-01-01 synthetic INVALID_CONFIG: broker rejected topic\n' > /tmp/sa-synthetic.log
sa investigate --state-dir "$HOME/.superagent" --prompt 'Investigate this synthetic configuration failure' --evidence /tmp/sa-synthetic.log
sa show --state-dir "$HOME/.superagent" --id <investigation-id>
sa followup --state-dir "$HOME/.superagent" --id <investigation-id> --prompt 'Broker rejected the topic configuration'
sa stop --state-dir "$HOME/.superagent"
```

`sa investigate` returns an investigation ID and Trigger ID. `sa show` lists the Ticket, Assignment and validated findings; the model turn is asynchronous, so query again until `latestReport` becomes `waiting` (findings) or `failed`. Reuse the investigation ID for follow-ups. Set `SA_STATE_DIR` to avoid repeating `--state-dir` (default: `~/.superagent`). Evidence must be UTF-8 text, at most 64 KiB per file; the socket accepts at most four items per submission (the CLI currently accepts one `--evidence` file). State is private to the local OS account (directory `0700`, socket and evidence `0600`). Back up the state directory before migrating an existing SQLite database; schema 10→11 is handled by the existing transactional migration, and existing schema 11 records remain intact. On a pre-existing configuration, Superagent does **not** enable local intake or add your UID to Policy automatically; use a new state directory or explicitly configure the stored local Source and Policy. Do not reuse an existing state directory concurrently with another process.

## From inside Pi (opt-in)

After building, load this repository's extension for a one-off test with `pi --extension ./src/standalone/extension.ts` from the repo. Keep the daemon running (`node scripts/sa.mjs start`), and use the same `SA_STATE_DIR` in Pi and the daemon (default `~/.superagent`). For repeated use, `pi install .` adds the local package to your Pi settings; this is **optional** and should be done only after reviewing the extension. Restart Pi after installing. This does not auto-start the daemon or modify existing Tickets.

- `/ticket <goal>` proposes a Ticket and displays a confirmation; **no Ticket is submitted on decline**. `/tickets` lists local Tickets owned by your OS account in the current state directory, including Tickets created in other Pi sessions. Use `/board <ticket-id>` to inspect one and `/collaborate <ticket-id>` to explicitly resume it; neither command creates a replacement Ticket. If the list is empty, verify that Pi and the daemon use the same `SA_STATE_DIR` as when the Ticket was created. The CLI equivalent is `node scripts/sa.mjs tickets --state-dir <dir>`.
- `/task <ticket-id> <title>` proposes a review task; `/task <ticket-id> --code [--profile=name] <title>` creates a separately confirmed coder task with a fresh write-approved file scope. Profile names are discovered from owner Pi prompt templates (`PI_CODING_AGENT_DIR/prompts/*.md`, default `~/.pi/agent/prompts/`), with `default` requiring no template; they change instructions, never tools or file access. `/code-task` remains a default-profile alias. No Go tests run automatically. `/board <ticket-id> [page]` opens a dedicated Pi TUI viewer (not an overlay or bottom widget), refreshing the board snapshot every 1.5 seconds; the latest page names and shows the status of the three newest tasks. `/collaborate` opens the board viewer after approval. `/workspace-diff <ticket-id>` opens a dedicated per-file viewer with complete before/after snapshots (not a computed patch). In either viewer, use ←/→ for pages/files, ↑/↓ or PgUp/PgDn to scroll, and Esc to return to chat without pausing collaboration. Non-TUI notifications still warn for oversized snapshots. Board polling and viewers are read-only. During an approved `/collaborate` session, new persisted agent/owner messages and task transitions to `DONE` emit success-colored TUI notifications; checkpoints are not completion, and historical events are seeded on resume rather than replayed. `/discuss <ticket-id> <message>` posts an owner message after confirmation;
- `/ticket` creates a Ticket only after explicit approval, then seeds one task from its goal. `/collaborate <ticket-id>` asks separately for bounded collaboration and local `reviewer` approval; while Pi is open, it claims ready tasks for that approved reviewer and runs up to four turns automatically. The subagent has only `sa_agent_checkpoint` and `sa_agent_reply`, not coding/shell/file/network tools. Published checkpoints appear in Pi while work is underway and persist in `/board`; these are deliberate user-facing status updates, **not private reasoning**. `/pause-collaboration` stops the lease; `/proposal <ticket-id> <proposal-id>` decides a pending proposal before more work can run. Manual `/task`, `/approve-agent`, `/claim-task`, and `/next-agent` remain available as optional controls. The old `/run-agent` shortcut is disabled. A completed or ambiguous turn cannot be replayed automatically.
- `/ticket-followup <ticket-id> <text>` asks for approval to submit a new local Trigger on the existing Ticket's original Thread. Engine Subscription delivers it as an Input and the PiExecutor may create a new validated Assignment Report; board contents/diff are **not** injected automatically, so describe only verified outcomes and test status. This does not directly create a Report or a new Ticket.
- `/workspace-bind <ticket-id> <absolute-repo-root> [go|rust|cpp]` asks to bind an owner-controlled Git repository to an existing Ticket with an explicit language profile (default Go). Existing bindings remain Go-only. The local `reviewer` may then list **eligible tracked source filenames for that profile only** and submit a `files` proposal. `/proposal <ticket-id> <proposal-id>` separately approves **read-only** access to up to 12 concrete, clean tracked source files (Go: `internal/` or `cmd/` `.go`; Rust: `src/` or `tests/` `.rs`; C++: `src/`, `include/` or `tests/` `.cpp/.cc/.cxx/.h/.hh/.hpp/.hxx`); only then can their contents be sent to the configured Pi provider. `/workspace-write-approve <ticket-id>` requires another owner confirmation to permit direct edits to **all** granted original working-tree files. Legacy grants remain readable but cannot write until revoked and granted anew. It refuses files already changed outside this Ticket, symlinks, hidden/config/credential paths and changed HEAD. `/workspace-files <ticket-id>` lists approved paths and access mode; `/workspace-revoke <ticket-id>` removes a grant before any edit or pending write (use a new proposal for a narrower scope). `/workspace-diff <ticket-id>` displays approved before/after contents in a navigable, dismissible interactive Pi panel; oversized non-TUI notifications fail visibly. A durable pre-write intent prevents blind replay on interrupted edits; `/workspace-inspect <ticket-id> <path>` displays comparison hashes and state for manual recovery, but does not resolve the intent automatically. `/workspace-format <ticket-id>` runs only `gofmt` via stdin to check Ticket-written file formatting without changing the repo, after another UI confirmation. This is **not** a Go test. No Go test runner, arbitrary shell, commits, pushes, or multi-agent coding orchestration are provided. Check each proposed file for secrets yourself: a simple detector is not comprehensive. A completed/ambiguous turn is never replayed; after file approval, create a new owner-approved task for the continuation. An out-of-scope agent turn can record a `handback` reason and stop; it cannot authorize itself to expand scope. The workspace discussion/diff are **not** automatically promoted to an Engine Assignment Report or sent over a Channel.
- `/approve-external <ticket-id> <agent-id> <https-url> <TOKEN_ENV>` approves an outbound HTTPS endpoint. Set the **same** 32+-character token in the Pi and daemon processes' environments before approval. The endpoint receives `{version:1,ticketId,taskId,context}` via POST with `Authorization: Bearer <token>` and must return JSON `{message:string,done:boolean}`. Redirects and private-address destinations are refused. Do not use real data until you trust the endpoint and its operator.

The local Unix socket is owner-only; a second program running under the **same OS account** can still call it, including calling `resume`, `heartbeat`, or approval endpoints using a Pi session ID. The heartbeat is a presence/liveness hint, **not authentication or proof the Pi UI is open**. UI confirmations protect the Pi command workflow, **not all same-user processes**. Local agent messages and tasks are persisted in a Ticket-scoped board separate from Engine's Assignment lifecycle; the Engine-approved Ticket remains the authorization root. A session heartbeat keeps a 6-second lease active. Closing/replacing Pi pauses it; an expired lease or daemon restart requires a fresh `/collaborate` confirmation. Agent proposals to add tasks or invite agents are recorded in `/board` and stop further turns until `/proposal <ticket-id> <proposal-id>` approves or rejects them. Invite approval also requires separately approving the agent's identity and credentials. `/board` shows explicit explanation and event progress, **not private chain-of-thought**. A turn is bounded; the extension supervises ready work only during the current Pi session, **not as an unsupervised daemon background loop or an OS security boundary**. An ambiguous agent turn fails closed: create a fresh owner-approved task to try again.

## Architecture

```text
sa CLI → owner-only Unix socket → local Trigger → Policy gate → Engine.receive/decide
                                                     │
                                                     ├→ SQLite (Ticket, Thread, Mandate, Assignment)
                                                     └→ PiExecutor → restricted Pi AgentSession
                                                            ├→ authorized ticket context
                                                            ├→ ticket-scoped SHA-256 evidence read
                                                            └→ schema-validated findings → Engine.report → SQLite
```

SQLite Tickets are authoritative; each Ticket's Pi JSONL session path is supplemental and stored in SQLite. Follow-ups reuse the Ticket and previous findings. A durable turn marker fails closed on ambiguous interrupted runs; retry is a domain operation, never a blind duplicate model execution. An error leaves the Ticket inspectable with a `failed` report. A failed Assignment needs an explicit trusted in-process `Engine.retryTicket(ticketId)`; a follow-up alone will not rerun it. The local socket does not expose retry or arbitrary Ticket mutation.

## Security and limitations

The investigator has **application-level tool restrictions**, not OS isolation: only `sa_context`, `sa_evidence`, and `sa_report` are registered. The SDK resource loader disables discovery of project/global extensions, skills, context files and prompt templates. Built-in shell, file, write, network, MCP and delegation tools are not available. Evidence is digest-checked and only readable by an authorized Ticket reachable from its Trigger while evidence reading is enabled. Findings are validated before domain reporting. Evidence and prompts are untrusted inputs, and a compromised provider or process is outside this boundary. Pi authentication/model selection may invoke configured credential helpers or provider network access outside the investigator tool boundary. The optional workspace is an explicit Ticket-scoped language-profile file allowlist, not a whole-repo reader or OS sandbox. Existing Go bindings never expand to Rust/C++ automatically. There is no comprehensive secret redaction, evidence-retention/erasure policy, or remote channel UI.

See [migration audit and engineering risks](docs/010-standalone-migration.md). Run `pnpm check` for deterministic tests, build and dependency audit. To run a live synthetic smoke test, use the commands above with an authenticated Pi model and check `sa show` until a validated report appears.
